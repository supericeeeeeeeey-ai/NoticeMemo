# QQ 群通知自动监听：可行路线与边界

## 目标

在不增加群成员操作负担的前提下，持续获得“学院通知群”的新消息，并自动转成本地备忘录。

这件事的难点不在备忘录解析，而在消息来源：群不是使用者创建或管理的，应用不能默认拥有读取群聊的权限。

## 路线比较

| 路线 | 能否落地 | 主要限制 | 当前状态 |
| --- | --- | --- | --- |
| 后台剪贴板捕获 | 可以 | 仍需有人查看并复制消息 | v0.2.0 已实现 |
| 官方 QQ 机器人 | 有条件 | 需要群主/管理员授权，平台决定事件与消息权限 | 未接入 |
| 读取 QQ 本地数据库 | 不建议 | 隐私、加密、版本兼容、平台规则风险 | 明确不采用 |
| UI Automation 抓取窗口 | 不建议 | 界面变化、焦点冲突、后台不可靠、隐私暴露 | 明确不采用 |
| 注入进程或第三方协议 | 不建议 | 账号风控、封号、恶意外传、违反平台规则 | 明确不采用 |

## 当前方案：后台剪贴板捕获

NoticeMemo 使用 Windows 原生剪贴板格式监听：

1. 用户在 QQ 中复制一条群通知。
2. Windows 向 NoticeMemo 发出 `WM_CLIPBOARDUPDATE` 通知。
3. 程序读取剪贴板文本并做本地置信度判断。
4. 高置信度通知自动保存；其余进入托盘待确认队列。

这个方案的优点是不需要 QQ 账号凭据、不接触 QQ 进程、不读取聊天数据库，失败面小，也容易长期维护。缺点是“复制”仍是一个人工动作。

## 官方机器人路线

官方方向应参考 [QQ 机器人开发文档](https://bot.q.qq.com/wiki/)。接入前必须重新确认：

- 当前机器人类型是否支持目标群场景
- 谁有权把机器人加入群，以及是否需要群主/管理员操作
- 平台允许机器人接收哪些群事件，是否包含非 @ 的普通消息
- 是否需要公网回调地址、签名校验和应用审核
- 群管理设置是否允许机器人读取或响应消息

这些能力会随平台策略调整，不能把某个事件名或历史经验当成长期保证。即使在群内安装了官方机器人，也只有平台实际下发的事件才能进入本地备忘录。

未来若要接入，建议把机器人做成独立适配层：

```text
官方机器人回调 → 验签与白名单 → 规范化消息 → 本地 NoticeMemo 存储
```

并且需要群主/管理员的书面授权、最小化保存字段、明确的退出和删除机制。

## 明确不做的事

- 不读取或解密 QQ 本地聊天数据库
- 不注入 QQ 进程、不 Hook 消息函数
- 不使用 NapCat、Lagrange、OneBot 等非官方接入方式绕过平台权限
- 不通过 UI Automation 持续抓取聊天窗口
- 不把用户账号 Cookie、Token 或二维码登录凭据上传到第三方

这些方式可能短期“看起来能用”，但会引入账号安全、隐私、稳定性和合规风险，不适合作为长期项目的基础。

## “全天候”的实际含义

当前版本的运行边界是：

- Windows 用户已登录
- NoticeMemo 正在托盘运行，未被手动退出
- 已开启自动捕获
- 有人在 QQ 中查看并复制了通知

在满足这些条件时，捕获、解析、去重和保存不需要再切回 NoticeMemo。睡眠唤醒也不会丢失监听器；若开启开机启动，重新登录后会恢复后台运行。

它不会在无人查看 QQ 时自行发现新消息，也不会读取未复制到剪贴板的群聊内容。
